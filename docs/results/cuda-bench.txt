# CUDA GPU spike: should azgo get a CUDA BatchRunner? (2026-10-20)
#
# Machine: AMD Ryzen 7 7700X (8 cores, 16 threads), 30 GB, NVIDIA GeForce RTX
# 4070 Ti SUPER (16 GB, compute capability 8.9, 66 SMs), Windows 11 with
# WSL2 Ubuntu 24.04.4 LTS, CUDA 12.8, g++ 13.3, OpenBLAS 0.3.26. Otherwise
# idle. Program: tools/cuda_bench (source, build script and README there).
# Raw output follows the analysis. The Metal numbers come from
# docs/results/bench.txt (Apple M5 Max) and from the 13x13 run's
# selfplay-engines.csv. The Studio was not measured again: it was training
# that run, and measuring its GPU would have meant pausing it.
#
# ======================================================================
# Summary
# ======================================================================
#
# 1. A hand-written fp32 SGEMM in the Metal kernel's style is
#    batch-independent on CUDA, by construction and by test. It walks K from
#    0 to K in steps of 16 through shared memory, never splits K, and each
#    output is one fmaf chain in k order. A sample's output columns alone
#    and inside batches of 8, 144 and 256, at three positions, were bitwise
#    equal for every stem and trunk shape of the four networks. So were a
#    repeated run and all three tile shapes (32x256, 64x128, 128x128).
#    Against a double-precision reference its worst relative error is
#    0.8-1.4e-7.
#
# 2. cuBLAS (fp32, default math mode, no TF32) is not batch-independent. A
#    sample's columns alone differ from the same columns in a batch in
#    75-95% of elements, for every shape (repeated runs are equal). cuBLAS
#    picks other kernels for other N, and a whole pass through it gives
#    193-1060 different outputs for a position alone and in a batch. It is
#    a speed ceiling only, the same finding as Apple's MPS.
#
# 3. Gemm speed at batch 256 (trunk shapes, GFLOP/s): the hand kernel
#    reaches 11,800-16,300 (best tile), cuBLAS 17,500-25,300. The hand
#    kernel runs at 0.64-0.69x cuBLAS's rate: single-buffered, scalar global loads, no
#    tuning. At batch 8 the grid is too small to fill 66 SMs (0.5-8 TFLOP/s).
#
# 4. A whole inference pass, two slots kept full (the hub's case), evals/s:
#
#    net           batch  hand explicit  hand fused  cuBLAS+im2col  | Metal M5 Max 2-slot   hub
#    9x9 6x64        256         75,500     129,300         90,000  |        63,300        57,400
#    9x9 6x96        256         41,200      48,400         50,800  |        30,400        29,400
#    13x13 6x96      256         19,100      30,800         24,500  |      ~14,600 (a)   14,200 (b)
#    19x19 10x128    256          4,460       6,780          5,630  |         2,830         2,780
#
#    "explicit" writes the column matrix (im2col) and runs bn_relu after
#    each gemm, as the Metal backend does. "fused" is one implicit-GEMM
#    kernel per convolution. It reads the layer input through the im2col
#    index arithmetic and applies batch norm, the skip and ReLU in its
#    epilogue. Its outputs are bitwise equal to the explicit pass, and it
#    is just as batch-independent. The explicit pass spends ~42% of its
#    time outside the gemms, writing and re-reading 150 MB of columns per
#    13x13 6x96 layer at batch 256. The fused pass is 97% convolution.
#    (a) bench.txt's 9x9 6x96 2-slot rate scaled by area (81/169).
#    (b) the measured local/metal engine of the 13x13 6x96 run in real
#        self-play: 13,300-14,300 evals/s over generations 1-18 (296 games
#        at once, 800 simulations). The two M4 minis give ~2,400 each, so
#        the three Macs together give ~19,000.
#
# 5. Estimate for a CUDA engine on 13x13 6x96 at batch ~256: about 30,800
#    evals/s with the fused hand kernel as it stands. That is 2.1x the
#    Studio's GPU, 13x a mini and 1.6x the whole current cluster. A
#    cuBLAS-class gemm (0.41 ms instead of 0.62 ms per trunk layer) would
#    give ~45,000. Real self-play loses a few percent to the hub and to MCTS
#    on the CPU: the Studio's real 14,200 is ~97% of its raw 14,600. The
#    risk on this PC is the CPU side, which must feed 30k evals/s from 16
#    threads. Random playouts on 13x13 run at 302k moves/s here, against
#    ~360k on the M5 Max (interpolated between its 9x9 and 19x19 rates),
#    so it should keep up. Small passes (batch 8: 3,500 evals/s, 2.3 ms)
#    are latency-bound, so the engine needs many games in flight, as metal
#    does (every game of the slice at once).
#
# 6. The PC's CPU as a blas engine (OpenBLAS, single-threaded per worker,
#    batch 8, Network::infer, 13x13 6x96): 358 evals/s on one worker; 661,
#    1,235, 1,619, 1,898, 1,964 and 1,826 on 2, 4, 6, 8, 12 and 16
#    workers. It peaks at about 1,900-2,000 with 8-12 workers. That is ~0.8
#    of a mini's GPU, and only if the hosts file gives it cpu_workers=8: a
#    remote's default rule allows 2 (661 evals/s). bench, one worker:
#    blas 366 evals/s, train step 549 ms; naive 86 evals/s, 1,437 ms. The
#    M5 Max's Accelerate does 2,796 evals/s on 9x9 6x96 on one thread
#    (~1,340 scaled to 13x13), ~3.7x a Ryzen thread.
#
# Recommendation: build a CUDA BatchRunner (backend = cuda, Linux, inference
# only) on the fused implicit-GEMM kernel with the Metal kernels' contract.
# Self-play is ~2,900 s of a ~4,100 s 13x13 generation, so the PC could take
# about 60% of the games, and self-play would drop to roughly 1,200-1,300 s.
# Use the hand kernel, not cuBLAS: cuBLAS is ~1.5x faster per gemm at batch 256,
# slower than the fused kernel per pass, and breaks the determinism
# contract.
#
# ---- k OpenBLAS workers at batch 8, 13x13 6x96 (one-off program) ----
# Each worker: makeBackend("blas") (one thread), its own Workspace and
# Network::infer at batch 8 on random {0,1} planes, as a self-play CPU
# engine runs; 4 s per k after 0.5 s warm-up; linked against build-blas.
#   blas workers  1  evals/s      358  per worker    358
#   blas workers  2  evals/s      661  per worker    330
#   blas workers  4  evals/s     1235  per worker    309
#   blas workers  6  evals/s     1619  per worker    270
#   blas workers  8  evals/s     1898  per worker    237
#   blas workers 12  evals/s     1964  per worker    164
#   blas workers 16  evals/s     1826  per worker    114
#
