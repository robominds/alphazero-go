# Metal GPU spike: should azgo get a Metal backend? (2026-10-08)
#
# Machine: Apple M5 Max, 18 CPU cores (6 super + 12 performance), 40-core GPU
# (Metal 4), 128 GB unified memory, macOS 27.0.1, Xcode 27 SDK.
# Program: tools/metal_bench (source, build script and README there); raw
# output of every section follows the analysis below.
#
# Conditions. The 9x9-scratch96 run (6x96, 18 workers, nice'd) was using the
# CPU throughout. It was paused (SIGSTOP, resumed with SIGCONT, about 1.5,
# 1.3 and 2.4 min) for the three sections that time the CPU: cpu1, cpuall,
# seam. The gpu and det sections ran beside it; GPU kernel times barely
# depend on the CPU, but the per-call wall times (commit + wait) and a few
# rows are noisy (e.g. 6x96 B=256 fwd block, hand: 1.36 ms per call against
# 0.74 ms batched). Medians of >= 0.5 s per measurement.
#
# ======================================================================
# Summary
# ======================================================================
#
# 1. A MetalBackend behind today's Backend seam (gemm on the GPU, everything
#    else on the CPU) gains nothing. Measured with the real Network: a 6x96
#    training step takes 409-426 ms against 424.5 ms on the CPU, and
#    inference at batch 8 gets slower (4.7-7.3 ms against 2.0-3.2 ms).
#    Gemm is only 18-42% of the CPU's time for a pass (29% of a 6x96 step:
#    125 of 424 ms). The other ~70% is im2col, col2im, batch norm and the
#    copies, single-threaded on the CPU. Copying the operands in and out
#    costs about as much as the GPU saves. (The Workspace's std::vectors are
#    not page-aligned, so Metal cannot wrap them without a copy.)
#
# 2. The GPU wins only when the whole pass runs on it: every layer as a
#    kernel on shared buffers, one command buffer per forward or backward.
#    6x96 training step at B=256: CPU 424.5 ms; GPU 36.3 ms with the
#    scalar-tiled hand kernel (11.7x), 28.7 ms with the simdgroup-matrix
#    hand kernel (14.8x), 22.2 ms with MPS for the gemms (19x). Those GPU
#    figures use stand-in BN, ReLU and loss kernels of the right sizes, so a
#    real port would come out somewhat slower.
#
# 3. Inference: a single CPU core is beaten even at B=8, but all 18 cores
#    together need a batch of about 50 per pass before the GPU passes them.
#    The 18 workers together reach only 14,554 evals/s on 6x96 (809 per
#    worker against 2,491 for one worker alone; the CPU's matrix units are
#    shared). The GPU, pipelined with 2 command buffers in flight at B=144,
#    reaches 21.5k (hand), 30.2k (simd) or 41.8k (MPS) evals/s, so 1.5x,
#    2.1x or 2.9x. On 6x64: 31.3k on the CPU against 52-75k on the GPU.
#
# 4. Determinism holds for the hand kernels, and they are bitwise identical
#    to Accelerate except where split-K reorders the dW sums. They give the
#    same bits in all 20 repeats. A position's logits and value are
#    identical alone, in a batch of 8 or in a batch of 256, verified end to
#    end through Network::infer. Every forward and dX gemm output is
#    bitwise equal to Accelerate's (both evidently compute one sequential
#    fma chain over k). dW with split-K differs from the CPU by up to 3.6e-7 in a gradient
#    of 0.6, and is closer to an exact (double) result than Accelerate. dW
#    without split-K is bitwise equal to Accelerate too, but 4-7x slower.
#    MPS is deterministic run to run, but a position's output depends on
#    the batch it is in (0/4 equal; the small-M Linear gemms), so it cannot
#    serve a batching evaluator under the project's determinism guarantee.
#    Accelerate itself is not batch-independent either (0/4 alone), which
#    is harmless today because each worker batches its own leaves.
#
# 5. Recommendation. Do not build a MetalBackend behind the current seam.
#    If GPU work is wanted, port the whole Network (forward, backward,
#    optimizer) to Metal for the training phase first. One thread at a
#    fixed batch of 256 needs no concurrency changes, and it takes the
#    training phase from 174 s to about 15 s. Use own deterministic kernels
#    (gather col2im, split-K fixed per shape, no atomics), not MPS. A
#    cross-worker batching evaluator for self-play and arena could come
#    second, for another 1.5-2.1x on network throughput. Expected time per
#    generation, using gen 1 of 9x9-scratch96 (self-play 235.6 s, train
#    174.3 s, arena 23.2 s; 433 s):
#        training on the GPU only:                       ~273 s   (1.6x)
#        + batching evaluator, simd kernel:              ~152 s   (2.8x)
#        + batching evaluator, scalar hand kernel:       ~199 s   (2.2x)
#        (MPS evaluator, not deterministic:              ~119 s   (3.6x))
#    The cost: a macOS-only second implementation of every layer (forward
#    and backward) in Metal and Objective-C++, kept in step with the CPU
#    one, plus asynchronous self-play (two batches of 144 leaves in flight
#    means about 36 games running at once on 18 threads). Note too that
#    ~70% of the CPU step is single-threaded non-gemm code, so CPU-side work
#    on im2col and BN would recover part of the training gain with no new
#    platform.
#
# ======================================================================
# Details
# ======================================================================
#
# Shapes (src/layers.cpp, src/network.cpp). The input has 2*8+2 = 18 planes,
# so the stem conv gemm has K = 18*9 = 162. A block conv is M = filters,
# K = 9*filters, N = 81*B. Backward, per 3x3 conv: dW = gemm(no, T) with
# M = F, N = 9F, K = 81*B, accumulated (beta 1); dX = gemm(T, no) with
# M = 9F, N = 81*B, K = F. A 6xF forward pass is 18 gemms (stem, 12 block
# convs, 2 1x1 head convs, 3 Linear); a training step is 53.
#
# Per gemm, 6x96 (ms; CPU = project BlasBackend, 1 thread; GPU "batched" =
# GPU time per gemm with 20 in one command buffer; "per call" = wall time
# for one command buffer with commit + wait):
#                         CPU 1T   CPU all |  hand   simd    mps   (batched)
#   fwd block  B=8        0.060    0.060   | 0.100  0.143  0.016
#                                per call  | 0.258  0.286  0.132
#   fwd block  B=144      1.870    0.937   | 0.451  0.313  0.155
#   fwd block  B=256      3.327    2.276   | 0.744  0.476  0.259
#   bwd dW     B=256      2.787    1.854   | 0.842  0.622  0.427
#   bwd dX     B=256      4.323    3.031   | 0.528  0.370  0.236
# The CPU gemm runs at ~0.8-1.8 TFLOP/s on one thread (the SME matrix unit);
# at B >= 144 the hand kernels reach 4-7 TFLOP/s (scalar), 5.5-10 TFLOP/s
# (simd) and MPS 10-15 TFLOP/s on the 9x9 shapes. On the 19x19 forward and
# dX shapes MPS falls to ~5-7 TFLOP/s and the simd kernel beats it. At B=8 a single gemm is too small for the GPU:
# the CPU's 0.06 ms beats every per-call GPU time.
#
# Call overhead: an empty command buffer costs 13.5 us (commit + wait); a
# buffer with one tiny kernel costs 129 us of wall time for 7 us of GPU work
# (wake-up and scheduling). A forward pass sent one kernel per command
# buffer (49 kernels) takes 6-8 ms even at B=8, against 0.9-2.2 ms as one
# command buffer. Any per-call design pays that.
#
# Whole forward pass on the GPU (one command buffer, ms) against the CPU
# (Network::infer, 1 thread):
#   6x96   B=8     CPU 3.21   | hand 1.83   simd 2.21   mps 0.88
#   6x96   B=144   CPU 57.5   | hand 7.40   simd 5.73   mps 4.33
#   6x96   B=256   CPU 110.6  | hand 12.47  simd 9.27   mps 6.97
#   6x64   B=144   CPU 34.8   | hand 3.32   simd 3.26   mps 3.39
# Break-even batch against all 18 CPU cores (14.5k evals/s, 6x96), fitting
# time = a + b*B through B = 8 and 144: hand B ~ 54, simd ~ 47, MPS ~ 16.
# Against one CPU worker, the GPU is ahead from B ~ 4.
#
# In the seam table, "gemm ms" is the mean over all calls including the two
# warm-ups and "total ms" the median, so at B=8 gemm can exceed total.
#
# Accelerate with all threads (cpuall): gemm up to 1.5x faster at B >= 144,
# but a 6x96 training step only goes from 424.5 to 386.8 ms (-9%), so it is
# no substitute. Its results are bitwise equal to one thread's (same gemm
# hashes in cpu1 and cpuall).
#
# The live run: 9x9-scratch96 logs train 174.3 s at gen 1 (181-196 s at
# gens 2-4). 400 steps x 424.5 ms = 170 s, plus validation inference
# (~18.6k fresh positions at gen 1, twice that later, at 2,315 evals/s on
# one thread at B=256 = 8-16 s), which matches. Self-play at gen 1 played
# 200 games x 92.9 plies with 200 simulations per move: at most 3.7M
# evaluations, i.e. at most ~256 s at the 18-worker rate of 14.5k evals/s.
# It took 235.6 s, so self-play is almost entirely network evaluation; the
# projections above assume 90% of self-play and arena time is the network.
#
# Projection arithmetic (gen 1). Training on the GPU: 400 x ~29-36 ms
# + ~1 s validation = ~13-16 s (taken as 14). Batching evaluator: self-play
# and arena scale by 0.1 + 0.9/r with r = 2.07 (simd), 1.48 (hand),
# 2.87 (MPS), from the pipelined B=144 rates against 14.5k:
#   simd: 235.6*0.535 + 14 + 23.2*0.535 = 126 + 14 + 12 = 152 s
#   hand: 235.6*0.708 + 16 + 23.2*0.708 = 167 + 16 + 16 = 199 s
# Bit-identical-to-CPU training (dW without split-K: 3.2 ms hand, 4.7 ms
# simd per dW gemm, 12 per step) would add ~30-50 ms to a step: ~65-80 ms,
# still 5-6x faster than the CPU.
#
# 19x19 10x128 for reference: one CPU thread does 229-254 evals/s and a
# 4.23 s training step; the GPU (simd, one command buffer) does 2.9k evals/s
# at B=256 and a 280 ms step (15x).
#
# What was not tried: Metal 4 tensor operations
# (MetalPerformancePrimitives, the M5 GPU's per-core matrix hardware),
# fp16/bf16, and fusing im2col into the gemm (implicit convolution). Each
# could raise the GPU figures further; none changes the conclusion about
# the seam.
#
# Raw output follows, one section per process, in the order run.
