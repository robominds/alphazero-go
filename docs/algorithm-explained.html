00

The state

concept — the rules as a state machine, and what the network sees

Tic-tac-toe has 5,478 legal positions; you can print them all. Go on a 5×5 board already has about 4×10¹¹, and on 19×19 about 2×10¹⁷⁰. Nothing in this project enumerates positions. What it needs from the rules is much smaller: given a position, which moves are legal, what does a move do, and who won when the game ends. This chapter is those rules, stated the way a programmer needs them, and then the encoding that turns a position into numbers.

Groups, liberties, capture. Stones of one color that touch horizontally or vertically form a group. The empty points next to a group are its liberties. A move places a stone on an empty point (or passes). Then every opponent group left with no liberties is removed — captured. In the diagram below (GTP coordinates: columns A–E, rows 1–5 from the bottom), White's stone at C4 has one liberty left, C5. It is "in atari", and Black C5 would capture it.

Suicide. If, after removing captured opponent stones, the moved stone's own group has no liberties, the move is suicide. Strict Tromp-Taylor rules allow it (the suicidal group simply disappears); most human rulesets forbid it, AlphaGo Zero did, and so does this code. A suicide can only ever lose stones, so forbidding it removes a whole family of pointless moves from every search without costing any strength. Note the order of the check: captures first, then the liberty test. A move into a point with no empty neighbors is legal if it captures something, because the capture frees a liberty.

Board::isLegal answers "is this move locally legal" without playing it, by looking at the four neighbors:

bool Board::isLegal(int action) const {
    if (action == passAction()) return true;
    if (action < 0 || action > passAction()) return false;
    const int p = pad(action);
    if (cells_[p] != Color::Empty) return false;
    const Color me = toMove_;
    const Color them = opponent(me);
    // The new stone survives if any neighbor gives it a liberty:
    //  - an empty neighbor is a liberty directly;
    //  - an opponent group whose only liberty is p gets captured, freeing a point;
    //  - a friendly group with another liberty besides p lends it one.
    for (int d : kDirs) {
        const int q = p + d;
        const Color c = cells_[q];
        if (c == Color::Empty) return true;
        if (c == them && countLiberties(q, 2) == 1) return true;
        if (c == me && countLiberties(q, 2) >= 2) return true;
    }
    return false;  // suicide
}

countLiberties(q, 2) flood-fills the group at q and stops as soon as it has found two liberties: legality only ever needs to know "none", "exactly one" or "at least two". Groups are not maintained incrementally (no union-find, no chain lists). A flood fill over at most 361 points takes microseconds, while one network evaluation takes tens of microseconds on 5×5 and milliseconds on 19×19 (chapter 01), so the simpler code costs nothing that matters. bench measures the rules engine alone at 1.3 million random moves per second on 5×5 and 178,000 on 19×19, including legality, superko and hashing (docs/results/bench.txt).

Playing the move is the same logic with side effects — place the stone, then remove each neighboring opponent group left without a liberty:

int Board::play(int action) {
    assert(isLegal(action));
    /* ... a pass only flips toMove_; otherwise p = pad(action), me, them ... */
    cells_[p] = me;
    hash_ ^= zobristKey(p, me);
    int captured = 0;
    for (int d : kDirs) {
        const int q = p + d;
        // A group already removed via another neighbor reads Empty here.
        if (cells_[q] == them && countLiberties(q, 1) == 0) captured += removeGroup(q);
    }
    /* ... assert the new stone has a liberty, flip toMove_, return captured ... */
}

The padded array and the Off sentinel. Board size is a runtime value from 5 to 19, but the storage is always a 21×21 array: the largest board plus a one-point border. Every cell outside the playing area holds the color Off.

Board::Board(int n) : n_(n), toMove_(Color::Black), cells_(), hash_(0) {
    assert(n >= kMinBoardSize && n <= kMaxBoardSize);
    // Everything starts Off; only the n x n playing area is opened up. On a
    // 5x5 board the unused part of the 21x21 array stays Off as well, so it
    // behaves exactly like the sentinel border.
    cells_.fill(Color::Off);
    for (int p = 0; p < area(); ++p) cells_[pad(p)] = Color::Empty;
}

int Board::pad(int point) const {
    return (point / n_ + 1) * kStride + (point % n_ + 1);
}

The four neighbors of a padded index p are p − 21, p − 1, p + 1 and p + 21 (kDirs). For any on-board point all four are valid array indices, and an off-board neighbor reads Off, which is neither empty nor a stone — so the flood fills above never need a bounds check, and a stone on the edge simply has fewer liberties, which is exactly Go's rule. One Board type serves every size, and it is a plain value (441 bytes of cells plus a few ints) that search copies freely.

Ko and positional superko. Captures make repetition possible. Here Black has just captured a White stone at B3 by playing C3 (before and after):

Black's new stone at C3 has one liberty, B3. If White could immediately play B3 again, it would capture C3 and recreate the position before the capture exactly, and the two players could trade captures forever. This shape is a ko. The simple ko rule forbids the immediate recapture; this code uses the stronger positional superko rule, the one Tromp-Taylor specifies: a move may not recreate any whole-board arrangement of stones that has occurred earlier in the game. It also covers the rare longer cycles (triple ko and friends) that the simple rule misses.

Checking "has this position ever occurred" naively means comparing boards. Instead, every position carries a Zobrist hash: one random 64-bit key per (point, color), generated once from a fixed seed, and the hash of a position is the XOR of the keys of all its stones. Placing a stone XORs its key in, removing one XORs it out, so the hash updates in O(1) per stone. hashAfter computes the hash a move would produce without copying the board, unless the move captures:

uint64_t Board::hashAfter(int action) const {
    if (action == passAction()) return hash_;
    assert(isLegal(action));
    const int p = pad(action);
    const Color them = opponent(toMove_);
    for (int d : kDirs) {
        const int q = p + d;
        if (cells_[q] == them && countLiberties(q, 2) == 1) {
            // The move captures: let play() work out which stones go.
            Board next = *this;
            next.play(action);
            return next.hash();
        }
    }
    // No capture: the only change is one new stone.
    return hash_ ^ zobristKey(p, toMove_);
}

A single Board has no memory of the past, so superko lives one level up, in Game, which keeps every position of the game and a hash set of the positions seen so far:

bool Game::isLegal(int action) const {

    // every position of this game so far.

Scoring: Tromp-Taylor area and komi. The game ends after two consecutive passes (or at a move cap of 2·n² moves, so that self-play always finishes). The final position is then scored by Tromp-Taylor area scoring: each player gets one point per stone on the board plus one point per empty point in regions that touch only that player's stones. Empty regions that touch both colors count for nobody. There is no judgment of which stones are "dead" — chapter 05 shows what that does to the games. The code first decides who owns each point (chapter 06 reuses that as a training target), and the score is the sum:

Board::areaScore() adds up those n² values: +1 for every point that is Black's, −1 for every point that is White's.

Black moves first, which is worth several points on 19×19, so White receives komi: Game::scoreForBlack() is areaScore() − komi, and the default komi is 7.5. The half point means a draw is impossible; an integer komi can produce an exact tie, which this code scores as a draw (chapter 05). How much the first move is worth depends on the board, and on 5×5 it is worth everything: 5×5 Go is solved, and perfect play gives Black the entire board, a win by 25 points. That is why the 5×5 preset uses komi 24.5 instead of 7.5 — chapter 05 has the evidence.

What the network sees: input planes. The network does not read a Board. It reads a stack of n×n planes of 0s and 1s, always from the point of view of the player about to move — the Go version of tic-tac-toe's "my stones / their stones" canonicalization:

  • for each of the last H positions (H = history, 8 in every preset): one plane of the side-to-move's stones and one of the opponent's stones — 2H planes;
  • a "Black to move" plane and a "White to move" plane, exactly one of which is all ones.

That is 2H + 2 = 18 planes. "Own" means the player to move now, in every history plane: the network sees the recent past through the eyes of the player who has to act.

void encodePlanes(const std::vector<const uint8_t*>& stones, int n, Color toMove,
                  int H, int sym, float* out) {
    /* ... asserts; zero the whole output; dest[p] = transformPoint(sym, p, n) ... */
    const uint8_t own = static_cast<uint8_t>(toMove);
    const uint8_t opp = static_cast<uint8_t>(opponent(toMove));
    const int available = std::min(H, static_cast<int>(stones.size()));
    for (int k = 0; k < available; ++k) {
        // "Own" is the player to move now, in every history plane, so the
        // network always sees the game from the perspective it must act in.
        float* ownPlane = out + static_cast<size_t>(2 * k) * area;
        float* oppPlane = ownPlane + area;
        const uint8_t* s = stones[static_cast<size_t>(k)];
        for (int p = 0; p < area; ++p) {
            if (s[p] == own) ownPlane[dest[p]] = 1.0f;
            else if (s[p] == opp) oppPlane[dest[p]] = 1.0f;
        }
    }
    // Planes 2H (Black to move) and 2H + 1 (White to move): exactly one is all ones.
    const int colorPlane = 2 * H + (toMove == Color::Black ? 0 : 1);
    float* plane = out + static_cast<size_t>(colorPlane) * area;
    std::fill(plane, plane + area, 1.0f);
}

Why history at all? The current stones alone do not say which moves superko forbids, or which stones were just captured; the last few positions do. Positions before the first move are all-zero planes. The sym argument rotates or mirrors the output (chapter 06); search always passes 0, the identity.

Why two color planes, one of them all ones? Because of how the first layer reads the board. It is a 3×3 convolution with zero padding: at an edge point, the three neighbors that would lie off the board are read as 0. In the stone planes, an empty point is also 0 — so without help, an empty point on the edge looks exactly like an empty point in the middle of the board, and the network cannot tell where the edge is. A plane that is 1 on every on-board point breaks the tie: the convolution sees 1s inside the board and padding 0s outside it, so every 3×3 window that overlaps the edge produces a different response. AlphaGo Zero used 17 planes with a single color plane that is all ones for Black to move and all zeros for White; with that encoding the edge signal vanishes whenever White is to move. Two planes, exactly one of them all ones, keep it on every turn and still say whose turn it is.

01

The two-headed guess

concept — function approximation with a residual convolutional network

As in tic-tac-toe, one network answers two questions about a position: a policy (a probability for each move: which moves look good) and a value (a number in [−1, 1]: the expected result for the player to move). Search uses the first to decide where to look and the second to stop looking.

Tic-tac-toe's network was a multilayer perceptron, 18 → 64 → 64 → {9, 1}. That design does not survive contact with Go. On 19×19 the input has 18 × 361 = 6,498 numbers; a fully connected first layer of any useful width would need millions of weights, and worse, it would have to learn "a stone in atari can be captured" separately at every one of 361 locations. Go's patterns mean the same thing wherever they occur (the edge aside, which the ones plane from chapter 00 makes visible). A convolution exploits that: one small filter, 3×3 points across all input planes, slides over the whole board, so a pattern learned once is recognized everywhere.

This is AlphaGo Zero's architecture, at a size a CPU can train:

The presets set the number of residual blocks (blocks), the filter count F (filters) and the value-head width V (value_hidden) per board size (in this document B always means the batch size): 3 × 32 with V = 32 on 5×5, 6 × 64 with V = 64 on 9×9, and 10 × 128 with V = 256 on 19×19 (configs/*.cfg). AlphaGo Zero used 20 or 40 blocks of 256 filters.

Convolution as im2col + gemm. A convolution could be written as six nested loops, but nearly all of a ResNet's time goes into one operation, and it pays to make it a single big one: general matrix multiply, gemm. The trick is im2col: copy every 3×3 neighborhood of the input into a column of a matrix, then the whole convolution is one multiplication of the weight matrix by that column matrix.

void Conv2d::forward(const Backend& be, const float* x, int B, int n, float* col, float* y,
                     ThreadPool* pool) const {
    const int M = B * n * n;
    // A 1x1 convolution needs no unfolding: x [cin][M] already is the column matrix.
    const float* columns = x;
    if (k != 1) {
        im2colChannels(be, pool, x, cin, B, n, k, col);
        columns = col;
    }
    // y [cout][M] = w [cout][cin*k*k] . columns [cin*k*k][M]
    gemmColumns(be, pool, false, false, cout, M, cin * k * k, 1.0f, w.data(), columns, 0.0f, y);
}

Column 0 is pixel (0,0)'s neighborhood with the five off-board entries filled with zeros — the zero padding. The 1×9 weight row times the 9×9 column matrix gives all nine outputs at once. With C input planes the column matrix has 9C rows, and with F filters the weight matrix has F rows, so a whole layer is one [F × 9C] · [9C × n²] product. Backend::im2col, which builds the columns, is plain memory shuffling, and so is its adjoint col2im; both are virtual with a shared default implementation. gemm is the one pure-virtual operation, the one each backend must supply: blocked loops in the naive backend, a call to cblas_sgemm in the BLAS backend (Apple Accelerate on macOS, which runs it on the CPU's matrix units).

Channel-major layout. Every activation in the network is stored as [channels][B][n·n]: all of channel 0 for every sample in the batch, then all of channel 1, and so on. That is not the order the caller supplies ([B][planes][n·n], one sample after another), so forward transposes the input once:

void Network::forward(Workspace& ws, const float* input, int B, Mode mode) {
    /* ... be = backend, pool = ws.pool_, n, A = n * n, P = planes, M = B * A, col, convOut ... */
    // [B][planes][A] -> [planes][B][A]. Channel-major lets a conv treat the
    // whole batch as one wide matrix: one gemm per layer, not one per sample.
    parallelChunks(pool, P, [&](int p) {
        for (int b = 0; b < B; ++b)

With this layout the column matrix of a batch is just wider: M = B·n² columns instead of n², and one gemm computes the layer for every sample at once. It also makes batch norm, which works one channel at a time, read one contiguous run of B·n² floats per channel.

Batch norm, and the bug you get if you mix up its two modes. After each convolution, batch norm rescales every channel to mean 0 and variance 1, then applies a learned scale γ and shift β. It is what makes a deep stack of convolutions trainable at a reasonable learning rate. The question is: mean and variance of what? In training, of the current minibatch, per channel, over all B·n² values:

void BatchNorm2d::forwardTrain(const float* x, int M, float* y, float* xhat, float* invStd,
                               bool updateRunning, ThreadPool* pool, float momentum) {
    assert(M > 1);
    parallelChunks(pool, c, [&](int ch) {
        /* ... mean and biased variance of channel ch over its M values, in double ... */
        const float inv = static_cast<float>(1.0 / std::sqrt(var + kEps));
        invStd[ch] = inv;
        /* ... y = gamma * (x - mean) * inv + beta, saving xhat = (x - mean) * inv ... */
        if (updateRunning) {
            // Inference sees one position at a time, so it needs population
            // estimates: unbiased variance, exponential moving averages.
            const double unbiased = var * M / (M - 1);
            runMean[ch] = (1.0f - momentum) * runMean[ch] + momentum * static_cast<float>(mean);
            runVar[ch] = (1.0f - momentum) * runVar[ch] + momentum * static_cast<float>(unbiased);
        }
    });
}

In inference — every evaluation during search — it uses the running averages collected during training instead, which reduce to one fixed scale and shift per channel:

void BatchNorm2d::forwardInfer(const float* x, int M, float* y, ThreadPool* pool) const {
    parallelChunks(pool, c, [&](int ch) {
        // Fold the fixed statistics into one scale and shift per channel.
        const float scale = gamma[ch] / std::sqrt(runVar[ch] + kEps);
        const float shift = beta[ch] - scale * runMean[ch];
        const float* xc = x + static_cast<size_t>(ch) * M;
        float* yc = y + static_cast<size_t>(ch) * M;
        for (int i = 0; i < M; ++i) yc[i] = scale * xc[i] + shift;
    });
}

Mixing the two up fails in two different, quiet ways. Use batch statistics during search, and a position's evaluation depends on which other leaves happen to share its batch of 8 — or, at batch 1, every channel of a lone position gets normalized to mean 0 over its own n² points, erasing exactly the "is there more of this feature here than usual" information the network relies on. Forget to update the running statistics during training, and inference normalizes with the initial mean 0 and variance 1, so every layer sees activations at a scale it was never trained on. Neither bug crashes and both still produce legal moves. That is why Network has explicit modes — Infer (running statistics), Train (batch statistics, running statistics updated), Probe (batch statistics, nothing updated, for gradient checks) and Calibrate (below) — and why tests/test_network.cpp checks that inference is per-sample: the same position evaluated alone and inside a batch of four gives the same output.

Generation 0: statistics nobody has collected yet. The second bug happens even with correct code, once: at the very start of a run. Generation 0 is a freshly initialized network that has never taken a training step, so its running statistics are still mean 0 and variance 1, and self-play, the arena and the validation loss all evaluate it in inference mode. Its batch norms then do almost nothing. He initialization keeps a convolution's output at roughly its input's scale, but each residual block adds its output to its input, and the first block's input is not normalized at all. Through the 21 convolutions of a 10×128 network the activations grew until the value head's tanh saturated: +1.00 at the empty board and everywhere else, with a policy whose entropy was 0.009 nats (uniform over 82 moves is 4.41). On a 9×9 run that was enough to wreck the start: search trusted a value that never moved, the games ended after about 18 plies, mostly in early pass-pass endings whose exact Tromp-Taylor scores dominated the search, and the value loss went to 0.00 on those games. Training never recovered, with or without resignation. The 6×64 and 6×96 runs never saw it: with fewer blocks the unnormalized activations stayed small enough, by luck of scale.

The fix is to give generation 0 the statistics training mode would use. When a run starts from a random network (not one given with --init-from, and never on resume), Trainer::startNew runs one training-mode pass over a fixed batch of 256 positions and sets every batch norm's running mean and variance to the statistics of its own input in that pass. That is the same update as a training step's, with momentum = 1:

Residual blocks. Each block computes relu(x + F(x)), where F is two convolutions: the block learns a correction to its input rather than a whole new representation. The payoff is in the backward pass. Gradients flowing back through a plain stack of layers are multiplied by each layer's Jacobian in turn and tend to shrink or blow up with depth; through a residual block they also flow along the skip connection unchanged. You can see that line in the backward code below: dTrunk passes straight through and the convolution path adds to it. AlphaGo Zero's 40-block network would be very hard to train without it; this project's 3 to 10 blocks benefit the same way.

Growing a network without changing it. A residual block whose correction F(x) is exactly zero is an exact identity: the block computes relu(x + 0), and x is already the output of a ReLU, so relu(x) = x. F ends in a batch norm, y = gamma * xhat + beta, so setting gamma = 0 and beta = 0 in a block's second norm forces F(x) = 0 whatever its convolutions hold. growBlocks appends blocks built this way, so a trained 6-block network becomes a 10-block network that computes exactly the same policy and value, and training continues from there instead of from scratch. The new blocks are not stuck: the gradient of the loss with respect to gamma is sum(dy * xhat), which does not depend on gamma, so gamma and beta move on the first step, and once gamma is nonzero the gradient reaches the convolutions too.

Widening it. Width grows the same way, by copying instead of zeroing (Net2WiderNet). The heads. The policy head squeezes the trunk to 2 channels with a 1×1 convolution and then a fully connected layer maps those 2n² numbers to n² + 1 logits: one per point plus one for pass. It knows nothing about legality — occupied points get logits too — so something downstream must mask them (chapter 02). What depth and width buy, and what they cost. 02

Search corrects the guess

concept — planning with PUCT tree search, and search as policy improvement

A network's first guesses are close to random, and even a trained one has blind spots. Monte Carlo tree search checks the guess against the rules: from the current position it runs many simulations, each walking down the tree of moves to a position it has not looked at yet, asking the network about that one position, and backing the answer up the path it came down. After a few hundred simulations the visit counts at the root are a better policy than the network's raw prior, and that improved policy is both the move played and the training target. Tic-tac-toe's chapter 02 walks through this on a 9-square board; the algorithm here is the same, rebuilt around a flat node arena, batched evaluation (chapter 03) and Go's extra rules.

The tree lives in two flat vectors. A node (MctsNode) holds a Board, its parent's index, the ply and consecutive-pass count, and the range of its edges; an edge (MctsEdge) holds the action, the prior P, the visit count N, the value sum W and a virtual-loss counter. Everything refers to everything else by index, so there is no pointer chasing and no per-node allocation.

Selection: PUCT. At each node the descent takes the edge with the largest

Q(s,a) + c_puct · P(s,a) · √(Σ_b N(s,b)) / (1 + N(s,a))

where Q = W / N is the average result this move has produced so far (exploitation) and the second term is an exploration bonus that starts proportional to the network's prior and shrinks as the move gets visited. c_puct is 1.5 in every preset.

int Mcts::selectEdge(int nodeIndex) const {
    const MctsNode& nd = nodes_[nodeIndex];
    assert(nd.expanded && nd.numEdges > 0);
    // In-flight descents count as visits (and as losses, below) so that the
    // next descent in the same batch is pushed towards other edges.
    int parentN = 0;
    for (int i = 0; i < nd.numEdges; ++i) {
        const MctsEdge& e = edges_[nd.firstEdge + i];
        parentN += e.visits + e.virtualLoss;
    }
    // max(1, .) lets the very first descent from a fresh node follow the
    // prior instead of seeing an all-zero exploration term.
    const float sqrtN = std::sqrt(static_cast<float>(std::max(1, parentN)));
    int best = nd.firstEdge;
    float bestScore = -std::numeric_limits<float>::infinity();
    for (int i = 0; i < nd.numEdges; ++i) {
        const MctsEdge& e = edges_[nd.firstEdge + i];
        const int n = e.visits + e.virtualLoss;
        // Each virtual loss adds a -1 result for the chooser. An unvisited
        // edge has Q = e.unvisitedQ: 0, except a known game-ending pass.
        const float q = n > 0 ? (e.valueSum - static_cast<float>(e.virtualLoss)) / n : e.unvisitedQ;
        const float u = cfg_.cPuct * e.prior * sqrtN / (1 + n);
        if (q + u > bestScore) {   // strict '>': the first index wins ties
            bestScore = q + u;
            best = nd.firstEdge + i;
        }
    }
    return best;
}

03

Batching the search

concept — virtual loss, and feeding the matrix unit big matrices

Serial MCTS evaluates one leaf per network call. On a CPU with a matrix unit, or on a GPU, that wastes most of the hardware: a call on one position is a skinny matrix product, and fixed per-call costs dominate. The fix is to collect several leaves and evaluate them in one call. The difficulty is that the descents are deterministic: with no new information in between, eight descents from the root would all follow the same path to the same leaf.

Virtual loss. While a descent is waiting for its leaf to be evaluated, every edge on its path counts one extra visit and one extra loss for the player choosing it (the virtualLoss terms in selectEdge, chapter 02). That lowers Q along the path and lowers the exploration bonus too, so the next descent is pushed towards other moves. When the batch comes back, the virtual losses are removed and the real values backed up. With a batch size of 1 there is never a descent in flight, and the algorithm is exactly serial MCTS; tests/test_mcts.cpp checks that batch size 1 calls the evaluator once per leaf and that batched searches leave no virtual loss behind.

void Mcts::search(const Game& game, Rng& rng) {
    assert(!game.isTerminal());
    prepareRoot(game);
    // The root needs priors before the first descent; evaluating it is not a simulation.
    if (!nodes_[0].expanded) evaluateLeaves({0}, rng);
    setRootPriors(rng);   // fresh noise (or none) for this search
    /* ... leaves, paths, path; done = 0 ... */
    while (done < cfg_.simulations) {
        /* ... clear this round's leaves and paths ... */
        // One round: up to batchSize descents, never more than the
        // simulations still owed. Each descent's virtual loss steers the
        // next one elsewhere.
        for (int d = 0; d < cfg_.batchSize; ++d) {
            if (done + static_cast<int>(leaves.size()) >= cfg_.simulations) break;
            const int leaf = descend(path);
            addVirtualLoss(leaf, path, +1);
            if (isTerminal(nodes_[leaf])) {
                // Exact value, no network needed: finish this simulation now.
                addVirtualLoss(leaf, path, -1);
                backup(leaf, path, terminalValue(nodes_[leaf]));
                ++done;
            } else if (nodes_[leaf].pending) {
                // Collision: another descent this round already waits on this
                // leaf. Undo and evaluate what we have rather than spin.
                addVirtualLoss(leaf, path, -1);
                break;
            } else {
                nodes_[leaf].pending = true;
                leaves.push_back(leaf);
                paths.push_back(path);
            }
        }
        if (leaves.empty()) continue;
        evaluateLeaves(leaves, rng);   // one evaluator call for the whole round
        /* ... for each leaf: pending = false, remove its virtual loss,
               back up its network value, ++done ... */
    }
    game_ = nullptr;
}

Collisions end the round. Virtual loss discourages repeats but does not forbid them: when one move is much better than the rest, a second descent can still land on a leaf that is already waiting. Evaluating it twice would waste a slot and double-count it, so the round stops early and evaluates the leaves it has. A terminal leaf never waits at all; its exact value is backed up on the spot. The cost of batching is a slightly different search: descents in a round cannot see each other's results. A batch size of 8 (mcts_batch in every preset) is a common compromise — small enough that the tree does not "go wide" much, large enough to fill the matrix unit better.

Why batch size matters to gemm. Take the 5×5 preset's residual convolution: its weight matrix is 32 × 288 (32 filters, 32 channels × 9 offsets). At batch 1 it multiplies a column matrix 25 wide; at batch 8, 200 wide. Both products cost the same per column, but the batch-8 call pays the fixed costs — the call itself, packing the operands, starting the matrix unit, and all the per-layer bookkeeping around it — once for eight positions instead of once for each. Measured on the M4, one thread, BLAS backend (docs/results/bench.txt, last table): the 5×5 network evaluates about 23,000 positions per second at batch 1 and 30,400 at batch 8; the 9×9 network about 2,750 and 3,700. Batching buys about 1.3× on this CPU — worth having, but modest: on one CPU thread the fixed costs are a small part of each call. Hardware with much higher fixed costs per call, such as a GPU, gains far more from batching, as the end of this chapter shows. bench measures inference at the MCTS batch of 8 (docs/results/bench.txt): 30,488 positions per second on 5×5 is 3,811 network calls per second, each covering a whole batch.

        //    wait (or they must be failed: after a failure or once the hub
        //    stops), or the hub stops with nothing in flight.
        dispatcherWake_.wait(lock, [&] {
            return anyCompleted() || (!queue_.empty() && (anyFree() || !failed_.empty() || stop_)) ||
                   (stop_ && !anyBusy());
        });

        for (size_t i = 0; i < slots_.size(); ++i)
            if (slots_[i].busy && slots_[i].completed) finish(slots_[i], static_cast<int>(i), lock);
        /* ... after a failure, or once the hub stops, every queued request fails ... */
        // 3. While a slot is free and requests wait: whole requests from the
        //    front of the queue, up to maxBatch positions, into one batch.
        for (size_t i = 0; i < slots_.size() && !queue_.empty() && failed_.empty(); ++i) {
            Slot& slot = slots_[i];
            if (slot.busy) continue;
            /* ... move requests to the slot while they fit in maxBatch ... */
            lock.unlock();

There are two slots, so one pass runs on the GPU while the next one fills. The flush policy is greedy: a pass is submitted as soon as a slot is free and anything waits. There is no timer and no "wait until every worker has asked". Under load, requests pile up while both slots are busy, so the next pass takes all of them and batches grow by themselves. Under light load nobody waits for company that may never come. And nothing can deadlock: a worker waits only for its own request, and a request only for a slot, which the GPU frees. To keep the GPU fed, workers = 0 means twice the cores with metal. A worker waiting for the GPU uses no CPU, so one group of searches runs on the CPU while the other waits on the GPU.

Self-play and exploration

concept — generating diverse experience without wrecking its quality

Self-play is the data generator: the current network, guided by search, plays both sides, and every position becomes a training example. Two mechanisms keep those games from collapsing into one repeated line.

Dirichlet noise at the root. Tic-tac-toe's chapter 03 showed why: the PUCT exploration bonus is proportional to the prior, so a move the network has learned to dismiss is never searched, never played, and never corrected. Before each self-play search, the root's priors are mixed with a random Dirichlet sample, 25% noise to 75% network:

    // dirichletScale spread over the legal moves, whatever the board size.
    const int area = eval_.boardSize() * eval_.boardSize();

Why α scales as 10/n². A symmetric Dirichlet sample over L moves with concentration α is a random probability vector; the smaller α, the more of its mass lands on a few moves. What matters for exploration is roughly α·L, the total concentration: a sample with α·L ≈ 10 looks like "a handful of moves get a real boost". The number of legal moves grows with the board, about n² early in a game, so keeping α·L constant means α = 10/n²: 0.4 on 5×5, 0.12 on 9×9, 0.028 on 19×19. AlphaZero reported the same rule of thumb — α in inverse proportion to the typical number of legal moves, 0.3 for chess, 0.15 for shogi and 0.03 for Go. Using 19×19's 0.03 on 5×5 would put nearly all of each sample on one random move; using 5×5's 0.4 on 19×19 would spread it almost evenly over 362 moves, adding the same sliver to every prior instead of singling out a few moves to explore. Tic-tac-toe used a fixed 0.3 over at most 9 moves.

Noise is added only at the root and only in self-play. The arena and analyze switch it off (addNoise = false): measuring strength and inspecting a position want the network's honest judgment. With tree reuse (below) the root was an interior node of the previous search, so it starts with its raw priors, and setRootPriors mixes fresh noise into them on every search.

More than one machine. Every self-play game is seeded by its index, deriveSeed(seed, g, kPhaseSelfPlay, i), and stored at its index. That rule was made so that the thread count could not change a game (chapter 08), and it also means a game does not care which process, or which machine, plays it. Distributed self-play (the selfplay_engines key) builds on that. A generation's games are cut into contiguous slices of indices, one per engine: a machine and a backend, such as local/metal or mini1/blas. Every slice runs the same function, playSelfPlayGames, either in the coordinator's process or on another Mac through the small selfplay program. What may not move is the engine. The GPU and BLAS compute the same network to within 1e-5, and an M4 and an M5 Max may differ in the last bits too. Over a few hundred moves, a last bit can change a move. If games went to whichever engine was free, the engine that played game i, and so the game itself, would depend on timing. So the assignment is fixed before any game starts, in integers, from the key and the number of games alone:

std::vector<Slice> assignGames(const std::vector<EngineSpec>& engines, int games) {
    /* ... fixed = the counts' sum, weights = the weights' sum; refuse
           counts above games, or a rest that no weighted item takes ... */
    const long long rest = games - fixed;
    /* ... */
    // 1. and 2.: the counts, in 64-bit integers (rest * w <= 10^12).
    std::vector<long long> count(n, 0), remainder(n, -1);
    long long given = 0;
    for (size_t e = 0; e < n; ++e) {
        if (engines[e].games >= 0) {
            count[e] = engines[e].games;
        } else {
            count[e] = rest * engines[e].weight / weights;
            remainder[e] = rest * engines[e].weight % weights;
            given += count[e];
        }
    }
    // Fewer leftover games than weighted items: each gets at most one, the
    // largest remainder first, the earlier item on a tie.
    for (long long left = weights > 0 ? rest - given : 0; left > 0; --left) {
        size_t best = n;
        for (size_t e = 0; e < n; ++e)
            if (remainder[e] >= 0 && (best == n || remainder[e] > remainder[best])) best = e;
        ++count[best];
        remainder[best] = -1;
    }

    // 3. Contiguous slices in list order.
    std::vector<Slice> slices;
    int first = 0;
    for (size_t e = 0; e < n; ++e) {
        if (count[e] == 0) continue;
        slices.push_back({static_cast<int>(e), first, static_cast<int>(count[e])});
        first += static_cast<int>(count[e]);
    }
    return slices;
}

Or one queue. Fixed slices have a price: a generation lasts as long as its slowest slice. Weights can set each engine's average, but a mini's 20 games of 19×19 vary in total length by several percent from one generation to the next, the weights are a person's estimate, and a failed remote moves its whole slice to one machine. selfplay_allocation = dynamic (opt-in; static stays the default) puts a generation's games in one queue instead. Nothing about a game changes: game i is still seeded by its index and merged at its index; only who plays it is decided while the generation runs. Each engine keeps up to its concurrency of games in flight (for a GPU engine, enough to keep its passes full) and takes the lowest queued index whenever one of its games ends, so a fast engine simply takes more. A remote engine runs one selfplay --stream process for the whole generation, which receives play <index> lines and sends each game back the moment it ends, verified as a result file's games are. When a remote fails, only its games in flight go back to the queue.

A plain first-come queue balances the middle of a generation but not its end. An engine with many games in flight takes a long time over each one: the PC, with 128 at once, about 7,000 s per 19×19 game. Handed one of the last games, it finishes long after everyone else. An engine's latency is its mean time from handout to finished game, measured during the generation. If the engine would finish the game before the last game already in flight ends, it gets it. Learning from itself

concept — supervised learning on self-generated labels, with a replay buffer

Once positions carry (π, z) labels, training is ordinary supervised learning on the loss from chapter 01. The Go-specific questions are where the examples live, how they are drawn, and how hard to train on them.

A replay buffer of whole games. Tic-tac-toe's buffer held encoded examples. Here an encoded example is 18 planes of n² floats — 26 KB on 19×19 — while the position itself is n² bytes, and the 16 history planes are just the previous 8 positions of the same game. So the buffer stores whole games (GameRecord: the moves, one byte per point per position, the sparse visit counts and the result) in a sliding window of at most buffer_positions positions, evicting the oldest games first. Symmetry augmentation. Go's rules, and komi, are unchanged if the board is rotated or mirrored, so each position has up to 8 equivalent versions with the same value and correspondingly transformed best moves. Showing the network a random one of the 8 multiplies the data for free:

int transformPoint(int sym, int point, int n) {
    assert(sym >= 0 && sym < kNumSymmetries);
    assert(point >= 0 && point < n * n);
    int row = point / n, col = point % n;
    if (sym & 4) col = n - 1 - col;               // mirror left-right first
    for (int turn = 0; turn < (sym & 3); ++turn) {
        // One clockwise quarter turn: the top row becomes the right column.
        const int r = col;
        const int c = n - 1 - row;
        row = r;
        col = c;
    }
    return row * n + col;
}

Learning or memorizing? Those losses are measured on batches from the replay buffer, the very data SGD is fitting, and each position there is drawn several times (5.8 on average in the late 9×9 runs). So a falling training loss cannot tell better judgment from a closer fit to the window. Supervised learning answers that with a held-out set, and self-play makes one every generation: the new games, which the network has never trained on. With validation_loss = true (the default), right after self-play and before those games join the buffer, the trainer scores the network about to train on them, generation g − 1's, on every one of their positions: the same cross-entropy and squared-error terms as the training loss, with batch norm in inference mode and no symmetry augmentation (heldOutLoss in src/validation.cpp). It scores the same network the same way on as many positions drawn from its training distribution, the buffer it trains on. The gap between the two (val_* against seen_* in log.csv) mixes what training on that window bought with the difference between older games and fresh ones; a gap that widens while the held-out loss stalls is overfitting. Nothing feeds back: the algorithm is AlphaGo Zero's, unchanged, and every checkpoint is byte-identical with the measurement on or off.

An auxiliary target: ownership. Every 9×9 network so far fails the eye check (docs/results/README.md): it rates White's B1, which kills a Black group on the bottom edge, about the same as Black's B1, which gives the group two eyes. That is a life-and-death judgment, the value head's job, and the value head learns it from one number per position, the game's result z = ±1. That signal is weak in two ways. It is noisy: a position's z also depends on every later move of both sides, so a position that was won gets −1 whenever the game was thrown away afterwards. And it is slow: under Tromp-Taylor rules a dead group only costs points once it has actually been captured (chapter 05), so "this group has one eye" and "this game was lost" can be dozens of moves apart.

KataGo (David J. Wu, Accelerating Self-Play Learning in Go, 2019, arXiv:1902.10565) trains its network on auxiliary targets next to π and z. The simplest is ownership: for every point, who owns it when the game ends. The final board already holds the answer, and chapter 00's Board::ownership computes it, so each game now carries n² labels (GameRecord::finalOwnership, from Black's view) instead of one. Every point of a group that died is labelled with the opponent's color, which is the life-and-death lesson in its most direct form.

Measuring progress without an oracle

concept — relative evaluation — arenas, Bradley-Terry Elo and confidence intervals

Tic-tac-toe could be scored against a perfect minimax player. Go cannot (5×5 is solved, but no solver ships with this project, and 9×9 and 19×19 are not). The only yardstick left is the network's own past: each new generation plays earlier ones, and ratings are fitted to the results. This chapter is about how much that can and cannot tell you.

The arena. Every generation (arena_every = 1), the new network plays arena_games games (20 in the 5×5 and 9×9 presets, colors alternating) against a few earlier generations and the fixed players (bots and reference networks, below), with search but without Dirichlet noise:

Choosing informative opponents. Playing only g − 1 measures one step at a time, and small errors add up. Playing everyone is too expensive. So which earlier players are worth twenty games? A game the new network wins with probability p has a result with variance p(1 − p), and that is how much it can tell you: 0.25 at p = 0.5, 0.21 at 0.7, 0.09 at 0.9, 0.01 at 0.99. A game against an opponent it beats 99% of the time is worth a twenty-fifth of an even game. The rating fit adds a second limit (next section): a 20–0 sweep can never say more than 400·log₁₀(41) ≈ 645 Elo. The reference runs in docs/results/ were made with a fixed ladder: g − 1, g − 2, g − 4, g − 8, and always generation 0. On 9×9, generation 0 scored at most 2 of 20 in every one of its 137 matches from generation 14 on, and 0 of 20 in 110 of all 150 matches (docs/results/9x9/results.csv). A yardstick from outside the lineage. The references can include uniform bots (bot_simulations, e.g. 100): MCTS players whose priors are all equal and whose value is always 0. A bot is a weak yardstick, though: in the 9×9 re-rate the 100-simulation bot scored at most 1 of 20 against every generation from 30 on and was never chosen after 43 (docs/results/9x9/rerate/results.csv), so the presets no longer include one. Reference networks (reference_networks) are frozen checkpoints, typically the best of an earlier run, played as fixed references after the bots: reference network j is player −(bots + j), ref1, ref2, … in the progress line. Each is read once and fitted to the run's shape with the growth operations of chapter 01 (wider, deeper, an ownership head added or dropped), which leave its policy and value unchanged (widening up to float rounding); a network bigger than the run's is refused. state.bin records a hash of each file, so a resumed run cannot swap one under an old ID. Selection, matches, refit and promotion are one function, runArenaRound (src/arena_round.cpp), which plays the matches that do not depend on each other at once (chapter 03). Training uses it, and so does train --run DIR --rerate, which replays the arena over a finished run's checkpoints into DIR/rerate/. With gating off, the arena never feeds back into training, so a re-rated run measures exactly the networks a live run would have.

Bradley-Terry instead of incremental Elo. Chess-style Elo updates each player's rating after every game by an amount proportional to the surprise. The result depends on the order the games arrive in, and it never revisits old ratings in the light of new evidence. This project instead keeps every pairwise result in a table (results.csv) and, after each arena round, refits all ratings at once by maximum likelihood under the Bradley-Terry model: P(i beats j) = γᵢ / (γᵢ + γⱼ), reported on the Elo scale as 400·log₁₀ γ, where a 200-point gap means about 76%. The fit is Hunter's MM algorithm:

std::map<int, double> fitBradleyTerry(const ResultsTable& results, int anchor) {
    /* ... 1. keep only players connected to the anchor through played pairs ... */
    // 2. Pair counts plus one virtual drawn game per played pair: n_ij + 1
    //    games, s_ij + 0.5 score. Without it a player who never lost would have
    //    an infinite maximum-likelihood rating.
    /* ... wins[i] (with the virtual halves) and one edge {i, j, games} per pair ... */
    // 3. MM iteration (Hunter 2004): gamma_i <- W_i / sum_j n_ij / (gamma_i + gamma_j).
    //    Each sweep increases the likelihood; rescaling keeps gamma_anchor = 1.
    for (int sweep = 0; sweep < 100000; ++sweep) {
        std::fill(denom.begin(), denom.end(), 0.0);
        for (const Edge& e : edges) {
            double d = e.games / (gamma[e.i] + gamma[e.j]);
            denom[e.i] += d;
            denom[e.j] += d;
        }
        for (size_t i = 0; i < m; ++i) next[i] = wins[i] / denom[i];
        /* ... divide by next[anchor]; stop when no gamma changes by 1e-10 in log ... */
    }
    /* ... elo[id] = 400 * log10(gamma) ... */
}

The published reference runs were measured with the 100-simulation bot as their only outside yardstick, before reference networks existed, so their Elo claims are essentially claims about their own lineage. External engines stay out of scope.

How noisy are 20 games? Wilson intervals. The log reports each match against g − 1 with a 95% Wilson score interval, which behaves sensibly for small samples and for scores of 0 or 1, unlike the textbook p ± 1.96·√(p(1−p)/n):

std::pair<double, double> wilsonInterval(double score, int games, double z) {
    if (games <= 0) return {0.0, 1.0};
    double n = games;
    double p = score / n;
    double z2 = z * z;
    // Center pulled toward 1/2 and a half-width that stays positive at p = 0
    // or 1: unlike p +- z*sqrt(p(1-p)/n), it behaves for small samples.
    double denom = 1.0 + z2 / n;
    double center = (p + z2 / (2.0 * n)) / denom;
    double half = z * std::sqrt(p * (1.0 - p) / n + z2 / (4.0 * n * n)) / denom;
    return {std::max(0.0, center - half), std::min(1.0, center + half)};
}

When the yardstick misleads: the 9×9 runs. An Elo curve anchored on generation 0 measures one thing precisely: how well each generation beats generation 0. On 9×9 that went wrong twice, in two different ways, and both times 100-game head-to-heads between checkpoints told the real story.

The first overnight run was made before the exact-pass rule of chapter 02 existed (its files are in docs/results/passbug/). Its curve said the network learned almost nothing and then got worse: the refit peaked at 288.4 at generation 35 and ended at 91.8 (docs/results/passbug/9x9-main/elo.csv), and the untrained generation 0 won 938 of the 3,000 arena games it played against trained generations (docs/results/passbug/9x9-main/results.csv) — about 7 of every 20 after generation 50. A trained network should not lose a third of its games to random weights. Two cheap checks located the problem:

  • Head-to-head instead of the anchor. 100 games of generation 150 against generation 30 ended 92–8, and against generation 60 89–11: the lineage was improving. Whatever was wrong lived in the games against generation 0, which the anchor-based fit spreads over every rating.
  • Reading the games. Generation 150 against generation 0 scored only 67/100, and an instrumented replay that wrote each move's search value and Tromp-Taylor margin into the SGF showed that every loss had the same shape. The trained network, clearly ahead on the board, passed while generation 0's hopeless stones were still standing in its area — Tromp-Taylor counts them, so the margin was against it — and generation 0 passed back and won on the count. docs/results/passbug/9x9-gen150-vs-gen0-loss.sgf is one such game: at ply 25 Black's search value is +0.93, the margin is −4.5, and Black passes.

A probe of that position found the blind spot. After its own pass, the network gave the game-ending reply (the opponent's pass) a prior of 0.0074 among 59 legal moves; with unvisited edges at Q = 0 and tried in prior order, 100 simulations never visited it, so the pass kept the network's optimistic Q of +0.88 and was played. Generation 0, with nearly flat priors, tried pass at its own root, found an exact win, and took it. The fix is the unvisitedQ rule of chapter 02; with it, the very same pre-fix checkpoints beat generation 0 100/100. The weights were fine; the search had a hole that only a strange opponent exposed, and the anchor turned that one opponent's quirk into the headline curve. docs/results/passbug/README.md has the full numbers.

  • The anchor's cap. With the virtual draw, a 20–0 sweep of generation 0 says "645 Elo above generation 0". 137 such near-sweeps pull every late rating toward 645, and the late refit values sit right around it.
  • Links too short to see the slope. At 4 Elo per generation, a generation should score 50.6% against g − 1 and 54.6% against g − 8; in generations 101–150 the measured means are 9.6 and 10.7 out of 20. Each of those 20-game links is ±150 Elo, so their combined pull is no match for the anchor's.

The full loop at scale

concept — a reproducible, crash-safe training loop, and what it costs

One generation is five steps, in Trainer::runGeneration:

It is AlphaGo Zero's loop run synchronously: no step overlaps another. An asynchronous actor/learner design would keep every core busy all the time, but this one reads as a list of plain steps, and it makes two guarantees that are hard to get otherwise: determinism and a clean resume.

Or pipelined. AlphaGo Zero itself ran its three parts at once: self-play with the best network so far, training on the latest games, and an evaluator that promoted a checkpoint once it won 55% against the best, after which self-play used it. While the evaluator played, self-play went on with the previous best. pipeline = on (opt-in; the presets leave it off) runs the same overlap without giving up either guarantee: generation g's steps 2–4 run on the trainer's thread while generation g+1's self-play runs on another, on the same engines, and one commit closes both. The overlap is decided by generation numbers, never by which part finishes first: self-play plays the best network of the last commit before it starts. Self-play of g+1 starts right after commit g−1, so it plays the best after the arena of g−1, one generation older than in the sequential loop. That lag is AlphaGo Zero's evaluator lag, moved to a generation boundary. Everything else is the sequential loop's: candidate g trains on the buffer with generation g's games, at generation g's learning rate, and v_resign for g+1 is calibrated from generation g's games before g+1's self-play starts. The commit of g therefore holds g+1's games, unprocessed (state.bin version 6):

A crash anywhere in an iteration loses that iteration's work, both halves, and the redo starts from exactly the committed state: the same games, the same network for the next self-play, the same v_resign. So a pipelined run interrupted at any moment resumes byte for byte, as the sequential one does (tests/test_pipeline.cpp crashes it at every step and kills it with SIGKILL in tests/integration_smoke.sh). What the overlap saves is the time the engines spent idle while the Studio trained (about 1,000 s per 19×19 generation) and the arena's under-filled waves, about 6–7% of a generation; the arena's games themselves are GPU work that the overlap moves but cannot remove.

Deterministic threading. Self-play and arena games run on W worker threads (all cores by default), which finish in an unpredictable order. The output is identical for any W anyway, because of three rules:

  • every random stream is seeded from its identity, never from its thread: game i of generation g's self-play uses deriveSeed(seed, g, kPhaseSelfPlay, i), training uses deriveSeed(seed, g, kPhaseTrain), the arena deriveSeed(seed, g, kPhaseArena, opponent);
  • results are stored by index, not by completion order;
  • the training phase, on threads of its own, cuts its work into chunks fixed by the data's shapes, never by the thread count, so every output value is computed by exactly one chunk with the same sequence of floating-point operations.

Trainer::playSelfPlay plays generation g's games as one slice, games [0, G), with playSelfPlayGames, which hands the range to playSelfPlayQueue as a source of game indices:

For a slice, the source counts through the range with an atomic counter and stores game i's record at index i; which worker plays game 17 varies from run to run, but game 17 itself does not.

Training has threads of its own. With BLAS, every training step used to run on one core: the BLAS backend is single-threaded, which suits self-play, where every worker already has a core to itself. Now runGeneration makes one ThreadPool trainPool(cfg_.effectiveTrainThreads()) — train_threads threads, 0 (the default) meaning every core — and hands it to the Workspace of the validation loss and of the training steps, to ReplayBuffer::sample and to SgdMomentum::step. The pool (include/azgo/parallel.hpp) starts its threads once, because a step is about a hundred short parallel loops, and lets them spin briefly, then sleep, between loops. ThreadPool::run(chunks, fn) (src/parallel.cpp) calls fn once per chunk, handing chunk indices out from an atomic counter as parallelFor hands out games, with the calling thread taking chunks too, and returns when every chunk is done. On an Apple M5 Max with 18 cores, a 9×9 step at batch 256 with BLAS went from 427 ms to 93 ms on a 6 × 96 network, and from 266 to 52 ms on the 6 × 64 preset (docs/results/bench.txt). Part of that is the rewritten loops alone, 323 and 201 ms on one thread: ReLU's backward lost a mispredicted branch per element, and im2col and col2im their per-pixel bounds checks.

Every layer cuts its loops into chunks fixed by the shapes, never by the thread count: a channel for batch norm and for im2col and col2im, a block of 512 gemm columns — 512 pixels — for a convolution's forward product and its input gradient, a run of 32,768 elements for ReLU, the residual sums and the SGD update, and 16 samples for per-sample work such as encoding the batch and the loss's softmax. The weight gradient, a sum over every pixel, is not cut into columns; it runs as one call beside the input gradient's blocks (the naive backend cuts it into bands of 16 output rows instead). The pool hands chunks to whichever thread is free, but each output value belongs to exactly one chunk and is computed with the same operations in the same order as on one thread. Sums over the whole batch keep their old order: batch norm sums each channel inside that channel's chunk, and the loss adds up its per-sample terms serially afterwards. A block of gemm columns is one plain gemm call on its own columns of C:

void gemmColumnBlock(const Backend& be, int block, int blocks, bool transA, bool transB, int M, int N, int K,
                     float alpha, const float* A, const float* B, float beta, float* C) {
    assert(blocks >= 1 && block >= 0 && block < blocks);
    const int j0 = block * kGemmColumnBlock;
    const int width = blocks == 1 ? N : (block == blocks - 1 ? N - j0 : kGemmColumnBlock);
    // Columns j0.. of op(B): further columns of B, or further rows when B is
    // stored transposed. A is shared by every block.
    const float* b = transB ? B + static_cast<size_t>(j0) * K : B + j0;
    be.gemm(transA, transB, M, width, K, alpha, A, transA ? M : K, b, transB ? K : N, beta, C + j0, N);
}

void gemmColumns(const Backend& be, ThreadPool* pool, bool transA, bool transB, int M, int N, int K,
                 float alpha, const float* A, const float* B, float beta, float* C) {

    parallelChunks(pool, blocks, [&](int block) {
        gemmColumnBlock(be, block, blocks, transA, transB, M, N, K, alpha, A, B, beta, C);
    });

Crash safety and resume. A network checkpoint alone is not enough to continue a run exactly; that also needs the optimizer's momentum, the replay buffer, the generation counter, the gating state, the arena table and, with resignation, v_resign and its window of disabled games. All of it goes into one file, state.bin, and state.bin is the commit point: a generation exists once its state.bin is on disk. Everything written before it (the checkpoint, SGF files, results.csv, elo.csv) may be left half-updated by a crash, and is then simply rewritten by the rerun of the generation with identical bytes — every random stream is derived from the seed, so the rerun is bit-identical. log.csv is appended after the commit; a crash between the two loses one human-facing row, never the run. (Pipelined, the commit of g also holds generation g+1's games, as above.) Every file is replaced with the same routine:

void writeFileAtomically(const std::string& path, const std::string& contents) {
    const std::string tmp = path + ".tmp";
    // Truncates any leftover .tmp from an earlier crash.
    const int fd = ::open(tmp.c_str(), O_WRONLY | O_CREAT | O_TRUNC, 0666);
    /* ... write all of contents, retrying on EINTR ... */
    // The data must be on disk before the rename makes it visible under path.
    if (!syncFd(fd)) fail("cannot sync " + tmp);
    /* ... close ... */
    // rename() replaces the destination in one step on POSIX file systems:
    // readers see the old file or the new one, never a partial write.
    std::error_code ec;
    std::filesystem::rename(tmp, path, ec);
    /* ... then fsync the directory, so the rename itself survives a power loss ... */
}

An honest comparison with AlphaGo Zero. AlphaGo Zero's strongest version trained a 40-block, 256-filter network for 40 days on 29 million self-play games, searching 1,600 simulations per move (its 20-block version: 4.9 million games in 3 days).
